α (alpha)Significance level — the pre-set false-positive rate: \( P(\text{reject } H_0 \mid H_0\ \text{true}) \) = Type I error. Typically 0.05.
β (beta)False-negative rate: \( P(\text{fail to reject } H_0 \mid H_0\ \text{false}) \) = Type II error. Power \( = 1 - \beta \). Typically β = 0.20 → 80% power.
t-testCompares a mean when the population SD is unknown (estimated by sample SD s) or n is small; t-distribution has fatter tails. \[ t = \frac{\bar X - \mu}{s/\sqrt{n}}, \qquad df = n-1 \] Same shape as z, with sample SD s in place of σ. At large n the two are indistinguishable — swapping t for z is never a fix for anything.
BootstrapResample with replacement, recompute the statistic → empirical sampling distribution → CI / SE, no distributional assumption. Answers “how big, and how sure?” Use when you want an interval on a median / ratio / skewed metric. (A Monte Carlo method.) Caveat: resampling doesn't fix a heavy tail — it faithfully reproduces it. A whale is either in your resample or not, so bootstrap CIs stay unstable. Capping fixes the tail; resampling only describes it honestly.
Permutation testShuffle the group labels to build the null distribution of the difference → p-value = fraction as extreme as observed. Answers “is there an effect at all?” — exact under the sharp null, assumption-free. Gives a p-value but NO confidence interval. Good for small samples / non-normal data.
Bootstrap or permutation?Permutation = hypothesis test. Bootstrap = interval estimate. An experiment readout almost always needs the effect size with uncertainty → bootstrap. Say it as: “permutation answers is there an effect, bootstrap answers how big and how sure.” Both are non-parametric, so neither rescues you from a heavy tail — pre-register a cap for that.
Critical values (z)Two-sided: 90% → ±1.645 · 95% → ±1.96 · 99% → ±2.576.   One-sided: 90% → 1.28 · 95% → 1.645 · 99% → 2.33. Reject H₀ if |z| > critical value. For sample-size / power: 80% power → \( z_\beta = 0.84 \), 90% power → 1.28.
Confidence intervalThe SE is the same denominator you used in the z-test — no new work. \[ \text{CI} = \hat\theta \;\pm\; z_{\alpha/2} \times \text{SE}(\hat\theta) \] worked — one sample vs a benchmark SLA target 24 hrs. Observed: n = 400, mean 25.2, sd 12. 1. SE = sd/√n = 12/√400 = 12/20 = 0.6  (not 12 — that's the SD) 2. margin = 1.96 × 0.6 = 1.18 3. CI = 25.2 ± 1.18 = [24.02, 26.38] 4. Excludes 24 — barely. Matches z = 1.2/0.6 = 2.0, also barely over 1.96. The test and the interval always agree. Two-sample: same recipe, but θ̂ is the difference. 6.0% vs 6.6% at n = 20,000 each → SE 0.00243 → CI [+0.12pp, +1.08pp], i.e. +2% to +18% relative. Report both units. SE, never SD. SD spreads individual observations; SE spreads your estimate. For a mean, SE = SD/√n — a factor of √n apart.
For two-sample tests the interval goes around the difference, not around either group.
Proportions: pooled SE for the test (under H₀ the rates are equal), unpooled for the interval (under the alternative they aren't). Common follow-up question.
CI and test always agree: excludes the null value ⟺ significant. Report the interval — the p-value says whether, the interval says how much.
MDE & sample size (Lehr's rule)minimum detectable effect\[ \text{MDE} = (z_{\alpha/2} + z_{\beta})\times \text{SE} \;\approx\; 2.8\,\text{SE} \] sample size per arm — means\[ n \approx \frac{16\,\sigma^2}{\Delta^2} \] sample size per arm — proportions\[ n \approx \frac{16\,p(1-p)}{\Delta^2} \] inverted: smallest effect a given n can detect\[ \Delta \approx \sqrt{\frac{16\,\sigma^2}{n}} \] worked — MDE from a finished test Two arms: n = 5,000 (sd 8) and n = 15,000 (sd 9). 1. SE = √(8²/5,000 + 9²/15,000) = √(0.0128 + 0.0054) = √0.0182 = 0.135 2. Critical difference = 1.96 × 0.135 = 0.26 — smallest diff you'd have to observe to call it significant. 3. MDE = 2.8 × 0.135 = 0.38 — smallest true effect you'd catch 80% of the time. Quote the MDE, not the critical difference. At an effect equal to 1.96×SE you only have 50% power. worked — sample size before a test Baseline conversion 6%. Want to detect a 10% relative lift. 1. Convert to absolute: Δ = 0.10 × 0.06 = 0.006  (pin down relative vs absolute first — it's where most of the error lives) 2. Variance from the rate: p(1−p) = 0.06 × 0.94 = 0.0564  (proportions need no separate σ) 3. n = 16 × 0.0564 / 0.006² = 0.9024 / 0.000036 ≈ 25,000 per arm (50,000 total) 4. Runtime at 4,000/arm/day = 6.3 days → run a full 7. Never run part-weeks; weekday and weekend users differ. Means version: sd 200s, detect 8s → 16 × 200²/8² = 10,000 per arm. 2.8 is for 95% two-sided at 80% power; use 3.24 for 90% power. The 16 is 2 × 2.8² ≈ 15.7 — the 2 is already in there for both arms, which is why going straight to the 16-formula stops you dropping the √2.
Don't confuse two things: 1.96 × SE is the critical difference — the smallest difference you'd have to observe to call it significant. 2.8 × SE is the MDE — the smallest true effect you'd catch 80% of the time. At an effect equal to 1.96×SE you only have 50% power.
Δ is squared — halving the effect you want to detect quadruples the sample. “Can we detect 1% instead of 2%?” is never a small request.
Always convert to runtime: n per arm ÷ daily traffic per arm = days. That's the answer a PM can act on.
Caveat: MDE is a design input computed before the test. Computing it retrospectively from the observed SE is a fair “what could this test have seen?” check — but observed power from the observed effect size is meaningless.
🎲 Probability

Bayes' theorem

Bayes' theorem\( P(A \mid B) = \dfrac{P(B \mid A)\,P(A)}{P(B)} \) — updates the probability of hypothesis A given evidence B. Denominator: \( P(B) = P(B\mid A)P(A) + P(B\mid \neg A)P(\neg A) \). Interview trick: reason with natural frequencies (counts), not the formula.
Shrinkage (empirical Bayes)The problem: ranking units by a rate when sample sizes differ wildly — the top of the list is all tiny-n units with extreme values (a seller with 3 orders and 1 defect = 33%; a restaurant with 3 reviews at 5.0).
The fix: pull each unit's estimate toward the population rate, weighted by its own volume. rates — Beta–Binomial posterior mean\[ \frac{x + \alpha}{n + \alpha + \beta} \] means / ratings — Bayesian average (C = global mean, m = prior weight)\[ \frac{vR + mC}{v + m} \] both are the same weighted average\[ w\cdot(\text{own}) + (1-w)\cdot(\text{population}), \qquad w = \frac{n}{n + \text{prior strength}} \] Intuition — pseudo-counts. α and β are fake observations credited to everyone before they start: “each creative begins with 10 clicks and 490 misses, and has to earn its way off the population rate.” One identical rule for all units, and volume-dependent trust falls out automatically.
Worked: population CTR 2%, prior strength 500 (α=10, β=490). 3/40 = 7.5% naive → (3+10)/(40+500) = 2.4%. Same 7.5% off 300/4,000 → 6.9%. Identical rate, opposite conclusions.
Picking the prior: empirical Bayes = fit the Beta to the observed spread of rates across all units (that's why it's “empirical”); or set α+β to “how many observations before I'd trust a unit alone.”
Alternatives: rank on the lower bound of a Wilson interval (small n → wide interval → low bound → sinks on its own). A hard volume threshold is the crude version: it excludes information and creates a cliff.
Same idea, other vocabulary: a random-effects / hierarchical model shrinks its fitted intercepts toward the grand mean by exactly this logic.
Self-critique to volunteer: shrinkage deliberately biases individuals toward the mean to cut variance — if the goal is spotting a genuinely exceptional new unit fast, it will hide it.

Distributions

⤷ Routing: counts vs waitsFirst ask: am I counting events, or waiting for one?
COUNTS — fixed trials → Binomial; events in a window with var = mean → Poisson; var > mean → Negative binomial.
WAITS — discrete trials until first success → Geometric; continuous time to next event → Exponential; time to the r-th event → Gamma.
The bridge: if events arrive Poisson(λ), the gaps between them are Exponential(λ) — counts and waits are two views of one process.
Waits carry two extra questions that counts never do: (1) is the hazard constant? (memorylessness — plot hazard by tenure); (2) who hasn't had the event yet? (censoring).
BernoulliSingle yes/no trial · param p · mean p, var p(1−p). One transaction: fraud or not.
Assumes: one atomic binary outcome, fixed p. Breaks when: the “trial” isn't atomic (a user can convert more than once) or p varies by unit.
Binomial# successes in n independent trials · params n, p · mean np, var np(1−p). # conversions out of N visitors — every conversion-rate A/B test. Note var < mean always — a variance above the mean rules binomial out.
Assumes: fixed n, independent trials, constant p. Breaks when: trials are correlated (sessions from one user, pages from one incident) or p varies across trials → over-dispersed → beta-binomial or cluster-robust SEs. Your CI is too narrow.
Poisson# rare events in a fixed interval · param λ (rate) · mean = var = λ. Fraud events per day. If over-dispersed (var > mean) → Negative Binomial.
Assumes: constant rate λ, independent events, equal exposure per unit. Breaks when: events arrive in bursts (one incident → ten pages); units differ in their rates (→ negative binomial); rate varies by time of day (→ non-homogeneous Poisson); units observed for unequal time (→ add an exposure offset, don't compare raw counts).
Geometric# trials until the first success · param p · mean 1/p, var (1−p)/p². PMF \( (1-p)^{k-1}p \). E.g. transactions until the first fraud.
Assumes: constant p every trial = memoryless (history tells you nothing). Breaks when: hazard changes with tenure — learning curves, cliffs, renewal dates. Plus censoring: units that never had the event are silently excluded.
NormalContinuous, symmetric; sums/means via CLT · params μ, σ² · mean μ, var σ². Sampling distribution of a mean.
Assumes: for a raw variable, symmetry; for a mean, that n is large enough relative to the skew. Breaks when: the tail is heavy enough that a handful of points dominate the mean — the CLT may hold technically while the estimate stays unstable. Never apply it directly to bounded or count data.
ExponentialTime between Poisson events · param λ · mean 1/λ, var 1/λ². Time between fraud attempts.
Assumes: memorylessness — constant hazard, waiting longer tells you nothing. Breaks when: arrivals cluster (after one page, another is far more likely within minutes) or the rate varies by time. Check: for a true exponential, var = mean². If the hazard isn't flat → Weibull (monotone), piecewise-constant (boundary spikes), Cox PH (covariates), Kaplan–Meier (just the curve).
UniformAll outcomes equally likely · params a, b · mean (a+b)/2. Random assignment / baselines.
Assumes: genuinely equal probability across the range. Useful check: p-values under a true null are Uniform(0,1) — so a histogram of A/A test p-values should be flat. A spike near zero means your pipeline is broken.
Negative binomialCounts that are over-dispersed — a mixture of Poissons because units differ in their rates (Poisson–Gamma). Mean = μ · Var = μ + μ²/r (r → ∞ recovers Poisson). Back it out: r = μ²/(Var − μ). Support tickets per customer, sessions per user, impressions per user — anywhere heterogeneity between units exists. Modelling it as Poisson understates variance → SEs too small → false significance.
Assumes: the over-dispersion comes from between-unit rate differences (Gamma-distributed λ). Breaks when: the extra variance is really within-unit bursting — NB will fit the marginal counts but the mechanism is wrong, so predictions and interventions mislead. Unequal exposure still needs an offset.
Compound Bernoulli (zero-inflated spend)Convert w.p. p; if converted, value has mean μ, variance σ²; else 0. expected value\[ E[R] = p\,\mu \] variance — law of total variance\[ \mathrm{Var}(R) = p\,\sigma^2 \;+\; p(1-p)\,\mu^2 \] Worked: p=0.05, μ=$80, σ=$40 → E = $4; Var = 0.05(1600) + 0.05(0.95)(6400) = 80 + 304 = 384, SD ≈ $19.6 — SD is 5× the mean.
The insight: 304 of 384 (≈80%) comes from the second term — whether they convert, not how much they spend. So attack the zero-inflation, not order values: split into conversion rate × value-given-conversion, or CUPED on pre-period spend.
Assumes: conversion and value-given-conversion are independent, and one purchase occasion per user. Breaks when: heavy buyers both convert more and spend more — that positive correlation adds a covariance term, so this formula understates the true variance. Multiple purchases per user break it too.
Links: Binomial = sum of n Bernoullis · Binomial ≈ Poisson when n large & p small (λ = np) · Poisson counts ↔ Exponential inter-arrival times.
🧪 Experimentation

Design & variance reduction

Factorial designTest multiple factors at once (e.g. 2×2) to get main effects + interactions. More efficient than one-at-a-time; the only way to catch interaction effects. Fractional = a subset of combos.
Hierarchical modelMultilevel / mixed-effects for nested data (users in cities in countries); partial pooling shrinks small-group estimates toward the global mean. Cluster-randomized / nested data → accounts for within-group correlation; stabilizes small segments.
CUPEDVariance reduction using pre-experiment data as a covariate → tighter CIs / more power at the same n. Regress out pre-period behavior before comparing groups.

Pitfalls & biases

Simpson's paradoxAn aggregate trend reverses when you split by a subgroup whose mix differs across groups (a confounder). Trust the segmented view — and in a randomized test it signals broken randomization.
Self-selection biasRespondents/participants differ systematically from non-participants; voluntary samples over-represent strong opinions (a.k.a. non-response / voluntary response bias). Fix: representative random sampling, or use behavioral data that covers everyone.
Interference (SUTVA violation)One unit's treatment affects another unit's outcome (social, marketplace, messaging) → contaminates control and dilutes / underestimates the measured effect. Fix: cluster / geo / graph randomization so effects stay within an arm.
Sample Ratio Mismatch (SRM)Observed split ≠ planned split (e.g. 52/48 vs 50/50) before any effect. Signals broken randomization or biased logging. Invalidates the test — check with a chi-square test, then debug before trusting any result.

Diff-in-Diff (DiD)Compare the before→after change in a treated group vs. a control group. Assumes parallel trends. Feature launched in one region at a known date.
Regression Discontinuity Design (RDD)Treatment assigned by a threshold; compare units just above vs. just below the cutoff. Eligibility cutoffs — strong local causal estimate.
Instrumental var. (IV)An instrument Z affects treatment X but touches outcome Y only through X → beats unobserved confounding (which PSM/regression can't). 2SLS: ① predict X from Z (keep only instrument-driven variation) → ② regress Y on that X̂. 3 conditions: relevance (Z moves X — testable, F>10) · independence (Z ~ as-good-as-random) · exclusion (Z hits Y only via X — untestable, the weak point). Estimates LATE (compliers only). Signature: units randomly assigned to a decision-maker / lottery of varying strictness (judge / loan-officer leniency, draft lottery), or randomized encouragement for adoption (the one you can design).
Intent-to-treat (ITT)Compare by what you assigned, ignoring what units actually did — everyone offered vs. everyone not. Unbiased, because it preserves the randomization. Diluted by non-compliance, but that dilution is real: it’s what launching actually delivers. The headline number for a ship / no-ship decision. Any offer, nudge or prompt a user can decline. ⚠️ Never compare accepters to control directly — that’s selection bias, and it typically overstates the effect several-fold.
Complier average causal effect (CACE) — a.k.a. local average treatment effect (LATE)The effect among compliers — those who take up because they were offered. CACE = ITT ÷ take-up rate. This is IV with random assignment as the instrument. Works because never-takers appear identically in both arms and cancel on subtraction — you never identify which control units would have complied, only how many. Assumptions: exclusion restriction (assignment hits Y only via take-up — the weak point, violated if the offer email itself motivates) · monotonicity (no defiers) · non-trivial first stage (tiny take-up → huge variance). Complier average causal effect (biostatistics) and local average treatment effect (econometrics) are the same estimand — pick one name and say it in full before using the acronym. Report ITT for the decision, CACE for the mechanism: ITT small + CACE large = a targeting problem, not a product problem.
Propensity matching (PSM)Matches each treated unit to a comparable untreated unit based on observed covariates (via the propensity score P(treated | covariates)), then compares. Observed confounders only; individual level.
Inverse probability weighting (IPW)Weight each unit by 1 / P(observed in its group) so the weighted sample resembles the full population — the weighting sibling of PSM (reweight everyone rather than discard unmatched units). Use when the outcome only exists for compliers (repayment rate, post-acceptance usage, satisfaction with a flow) so ITT is impossible — there is no control counterpart. Checks: overlap / positivity, and trim or stabilize extreme weights. ⚠️ Observed confounders only — same weakness as PSM. If take-up is driven by something unmeasured (cash need, growth ambition), it rebuilds the wrong comparison group. If you have a randomized offer, prefer IV / CACE — use IPW only for metrics that make ITT impossible.
Synthetic controlFor a single treated aggregate unit (a market): constructs a fake "twin" from a weighted combination of untreated markets matching the treated market's pre-launch trajectory, then compares post-launch lift. One treated market, many candidate controls, time-series.
Double MLLike PSM, makes each treated unit comparable to untreated — but uses ML to adjust for many complex / nonlinear confounders (orthogonalization + cross-fitting) → more robust than PSM. Observed confounders, but high-dimensional / messy.
CausalImpact (BSTS)Google's Bayesian structural time-series. Learns the pre-period link between the treated series and unaffected control series → predicts the counterfactual forward → impact = actual − predicted (with Bayesian credible intervals; pointwise + cumulative). Assumes control series are predictive but unaffected by the intervention, and the relationship holds into the post-period.
Uplift — conditional average treatment effect (CATE)Estimates the effect per segment or per unit, not on average — the tool for heterogeneous treatment effects (HTE) and for deciding who to target. ⚠️ Propensity ≠ uplift: targeting who is likely to convert spends budget on people who’d convert anyway. Four strata: sure things (convert regardless — pure cost) · persuadables (the only ones worth money) · lost causes · sleeping dogs (the offer makes them worse — reminds them they could leave, or trains them to wait for a discount). Methods: pre-registered subgroups + interaction tests (correct for multiplicity) → meta-learners (S / T / X) → causal forest. Requires a randomized holdback — without one, uplift is not identified at all. Pre-register subgroups or you’re fishing.
Selector (ask "how was treatment assigned?" first): threshold/cutoff → RDD · staggered rollout / clean before-after + control → DiD · single market + time series → synthetic control / CausalImpact · random assignment to a decision-maker of varying strictness, or randomized encouragement → IV · opt-in/self-selection with only observed confounders → PSM / double ML.
🤖 Modeling

Classification metrics

Precision\( \dfrac{TP}{TP+FP} \) — of everything we flagged positive, how much truly is. "How often we cry wolf."
Recall\( \dfrac{TP}{TP+FN} \) — of all actual positives, how much we caught (a.k.a. sensitivity, TPR). "How much we miss."
PR-AUCArea under the precision-recall curve across thresholds. Best summary for imbalanced / rare-positive problems.
ROC-AUCArea under the ROC curve (TPR vs. FPR). = P(model ranks a random positive above a random negative). 0.5 = random, 1.0 = perfect. Can look optimistic under heavy imbalance → prefer PR-AUC there.

Regression metrics

RMSE\( \sqrt{\dfrac{1}{n}\sum (y-\hat y)^2} \) — root mean squared error. Same units as target. Range [0, ∞), 0 = perfect. Penalizes large errors most (outlier-sensitive).
MAE\( \dfrac{1}{n}\sum |y-\hat y| \) — mean absolute error. Same units. Range [0, ∞), 0 = perfect. Robust to outliers.
MAPE\( \dfrac{1}{n}\sum \left|\dfrac{y-\hat y}{y}\right| \) — mean absolute % error. Scale-free. Range [0, ∞) as a % (can exceed 100%), 0 = perfect. Blows up when y is near 0.
R²\( 1 - \dfrac{SS_{\text{res}}}{SS_{\text{tot}}} \) — share of variance explained. Range (−∞, 1]: 1 = perfect, 0 = no better than predicting the mean, negative = worse than the mean. Pair with an error metric — never report alone.

Ranking metrics

Precision@kOf the top k results, the fraction that are relevant. "Are the top results good?"
Recall@kOf all relevant items, the fraction that appear in the top k. "Did we surface the relevant ones?"
NDCGNormalized Discounted Cumulative Gain — graded relevance + log position discount: \( DCG=\sum \dfrac{rel_i}{\log_2(i+1)} \), normalized by the ideal ranking → 0–1. Best for graded relevance (search / recs).
MAPMean Average Precision — binary relevance: average precision@k at each relevant rank, meaned over queries. Best for binary relevance.
MRRMean Reciprocal Rank = \( 1/(\text{rank of first relevant item}) \). Best for known-item search (one right answer).
Computed per query, then averaged. Offline proxies → confirm with an online A/B.

Methods

ClusteringUnsupervised segmentation by similarity. k-means (choose k via elbow/silhouette), hierarchical (dendrogram, no preset k), DBSCAN (density, finds outliers). Standardize features → choose k → profile clusters into actionable personas.
Monte CarloEstimate hard quantities by repeated random simulation (law of large numbers → empirical average converges to truth). Uncertainty with no closed form, power for complex designs, tail-risk / fraud loss distributions. Bootstrap is a Monte Carlo method.
Full model ladder (linear/logistic, trees, RF, gradient boosting, neural nets, recommenders) → see the 🎴 Flashcards.

Validation & leakage

Reduce overfittingOverfitting = high variance (memorizes training noise → train ≫ test performance). Fixes: more data · regularization (L1 / L2) · simpler model / feature selection · cross-validation for tuning · early stopping · dropout (NNs) · bagging / ensembles. Underfitting = the opposite: high bias, model too simple.
L1 vs. L2Penalty on weight size added to the loss (strength = λ, tuned by CV; higher λ = simpler model). L1 (Lasso) \( \lambda\sum|w| \) → drives weights to exactly 0 = feature selection / sparse. L2 (Ridge) \( \lambda\sum w^2 \) → shrinks smoothly, keeps all features, handles correlated predictors. L1 diamond has corners on the axes → zeros; L2 circle just shrinks. Elastic Net = both. Standardize features first.
Strategy vs. metricValidation strategy (holdout / CV / walk-forward) = HOW you split data to estimate generalization. Metric (precision, PR-AUC, RMSE…) = WHAT you compute on the held-out slice. Always used together.
HoldoutOne train/test split. Simple, cheap; fine for large data. Higher-variance estimate.
k-fold CVA partition into k disjoint folds (no replacement — every row in exactly one fold, tested exactly once); each fold is the test set once, average the k scores. Every point trains and validates → stable, lower-variance estimate. Best for limited data & tuning. Cost: k× training. NOT k random splits, and NOT with replacement — that's bootstrap. Clean pair: k-fold = without replacement, bootstrap = with.
Stratified k-foldSame k-fold mechanics, but each fold preserves the overall class ratio (e.g. 5% scam / 95% in every fold). Essential for imbalanced data (fraud) — else a random fold can land with too few/zero positives → garbage precision/recall on that fold. All three (holdout/k-fold/stratified) shuffle rows → IID only. Time-ordered data → time-based / walk-forward instead.
Time-based split (the principle)Pick one cutoff date → train on everything before, test on everything after (a.k.a. out-of-time split). This is the principle for time-ordered data: never learn from rows newer than what you score. One split → cheap, but a single noisy readout that depends on the cutoff you picked.
Walk-forward (the technique)The time-series answer to k-fold — apply the time-based principle repeatedly: roll the cutoff forward over several successive future windows & average → a robust multi-fold estimate (every fold still trains strictly before its test). Expanding window = train set grows each fold. Rolling / sliding window = fixed-length train window that moves — use when old patterns go stale (adversarial drift: fraud, scams). So: time-based = one cutoff (the idea); walk-forward = many rolling cutoffs (the robust operationalization). Never random k-fold on time data → lookahead leakage.
⚠️ Leakage — two familiesThe one test for both: "at prediction time, would I have this value, computed only from data that existed then?" If no → leakage.

① Feature problem — what goes into a row. Target/feature leakage: a feature encodes the outcome or is populated post-event (e.g. using #user-reports / was-taken-down to predict a scam app — those only exist after it went live). Symptom: perfect train score, collapses in prod (feature absent at scoring time). Also preprocessing leakage: fit scaler/encoder on train only.

② Split problem — how you divide the rows (features may be fine, but evaluation is optimistic). Temporal: train rows newer than test → model sees future patterns (fix: time-based / walk-forward). Group: same user/developer in train & test → memorizes the actor (fix: grouped split). Plus tuning on the test set (→ nested CV).

Overlap: a feature built with a look-ahead window (aggregating future rows) is both — a leaky feature whose leak is temporal. Fix: point-in-time correctness (aggregate only from data strictly before the timestamp).

🐍 Python — code comprehension

Edge cases — the six questions

1. What if it's empty?Zero rows after a filter or join, or an empty arm. Look for: len(x) in a denominator · .mean() / .std() on a possibly-empty Series · a groupby whose key may be absent. Usually returns NaN rather than raising — see the reference below.
2. What if there's only one row?Single-element arms and single-member groups. .std() uses ddof=1, so with n=1 it divides by zero → NaN. Any SE built on it is NaN, and every downstream comparison silently becomes False.
3. What if there are duplicates?Duplicate keys on either side of a merge multiply rows (many-to-many blow-up), inflating counts and re-weighting every mean. Also: groupby([id, group]) where group should be constant per id will silently emit two rows for a user assigned twice — and put them in both arms. That's what an SRM check catches.
4. What if a value is null?Ask the deciding question: is this missing, or is it a real zero? Assigned users with no events are zeros — fillna(0), never dropna(). Dropping them is a post-randomisation filter and breaks intent-to-treat. Any dropna() / .notna() / inner join between assignment and analysis deserves this question.
5. Does it mutate the input?In-place operations change the caller's object. list.sort() · .append() on a mutable default argument (created once at def time, shared across calls) · inplace=True · del while iterating a dict. Ask “is this a copy or a view?”
6. What's the complexity?Look for a filter inside a loop over unique keys — df[df.id == i] per user is a full scan each time, so O(n·m). Replace with one groupby / merge. Also say what you'd deliberately leave alone.

Silent failures — what actually happens (nothing crashes)

Any comparison with NaNNaN > 1.96 → False. NaN < 0.05 → False. The single most important one. A broken pipeline doesn't raise — it silently returns “not significant” / “don't ship”. Trace NaN all the way to the return value and say what the caller sees.
Empty Series.mean() → NaN · .std() → NaN · .sum() → 0.0, not NaN. The sum returning 0 is the nasty one: an empty group looks like a real zero.
Aggregations skip NaN.mean(), .sum(), .std() default to skipna=True. They don't error and they don't return NaN — they quietly shrink the denominator. Two metrics in one function can end up computed over different populations. If nulls are non-random, that's a bias, not a rounding issue.
count vs size.count() excludes NaN · .size / len() includes it. The gap between them is the null count — a free diagnostic.
Division by zeroPlain Python 1/0 → ZeroDivisionError. numpy/pandas floats: 1.0/0.0 → inf (warning only), 0.0/0.0 → NaN. So a zero baseline in a lift calculation usually returns inf rather than crashing — and inf then fails every comparison quietly.
Default merge is innermerge(...) with no how= is an inner join and drops unmatched rows. Between assignment and analysis that silently deletes assigned-but-inactive users. Same trap as SQL's LEFT JOIN + WHERE on the right table.
Sampling without replacementrandom.sample(xs, len(xs)) is a permutation, not a bootstrap — every resample has the identical mean. Bootstrap needs with replacement (random.choices / np.random.choice). Permutation is a different procedure testing a different null.
Standard error shapeAlways variance over n, then square root: (s**2/n)**0.5, i.e. s/√n. s/n is the classic planted bug — it makes SE far too small and z far too large. And for a difference, both arms contribute: (sA**2/nA + sB**2/nB)**0.5. One arm alone understates by √2.
Two-sided means abs()z > 1.96 and 1 - norm.cdf(z) are both one-sided. Correct: abs(z) > 1.96 and 2 * (1 - norm.cdf(abs(z))). Without it a strongly harmful result reports p ≈ 0.999 and “not significant” — you ship the harm. Drop the abs() and the two-sided p-value can also exceed 1, which is the tell.
💻 SQL — patterns & gotchas

Window patterns

Top-N / first per groupROW_NUMBER()/RANK() OVER (PARTITION BY key ORDER BY … ) → filter rnk ≤ N. ROW_NUMBER = exactly N (add a tiebreaker); RANK keeps ties (can return >N); DENSE_RANK = no gaps.
Period-over-periodLAG(x) OVER (ORDER BY period), then (cur/prev) − 1. The − 1 goes outside the OVER (…). ORDER BY lives inside OVER, not inside LAG().
Running total / shareAggregate first, then SUM(x) OVER (ORDER BY …) (running) or SUM(x) OVER () (denominator). Use SUM of the per-group count, not COUNT again.
Rolling window… OVER (ORDER BY d ROWS BETWEEN 6 PRECEDING AND CURRENT ROW). Counts rows not days → build a date spine for calendar gaps; COALESCE(x,0) so gaps count as 0.

Joins & gotchas

⚠️ LEFT JOIN + WHEREA filter on the right table in WHERE silently turns a LEFT JOIN into an INNER JOIN → put the filter in the ON clause (also how you put a time window on a join, e.g. retention).
Combine two event tablesAggregate each separately by day → join on date (avoids fan-out). Want all periods incl. one-sided? FULL OUTER JOIN + COALESCE(a.key, b.key) + COALESCE(metric, 0).
Rates after a LEFT JOINCOALESCE(numerator, 0) and NULLIF(denominator, 0) — otherwise a no-match row gives NULL, not 0.
"% that have a follow-up"Count the anchor rows meeting the condition: COUNT(CASE WHEN cond THEN id END), not the matched rows. "Next event per user" → LEAD, not a self-join.
Point-in-time activestart_ts < month_start AND (end_ts IS NULL OR end_ts ≥ month_start) — captures rows active as-of the date (incl. those that churn later). Current status ≠ status as-of-then.
⚠️ Small habitsRecency filter = ts ≥ DATE_ADD('day', −N, CURRENT_DATE) (not ≤) · COUNT(*) over COUNT(DISTINCT pk) · exact COUNT(DISTINCT) not approx_distinct at a threshold/flag · rolling-time distinct count → self-join on the range (can't window COUNT(DISTINCT)).

🏦 Merchant risk — how the loss actually happens

◆ Stripe is the backstop. The cardholder is always made whole — the only question is who funds it. Merchant balance first; if the merchant is gone, Stripe pays as acquirer. Stripe never took the money and never failed to ship, but the network makes the acquirer liable.

◆ It’s credit, not fraud. Payouts run in days; the dispute window runs in months. Every payout before that window closes is unsecured credit to a business onboarded in 90 seconds. That mismatch is the exposure.

◆ Exposure at default = volume already paid out, still disputable, not yet fulfilled. It compounds faster than revenue for a fast-growing merchant — which is why ramp velocity vs. peers is the load-bearing feature.

◆ Two of the four failure modes involve no fraud at all. Long fulfilment lag (furniture, travel, pre-orders) · bust-out (build trust, one huge burst, disappear) · honest insolvency · subscription abuse. So you’re underwriting solvency, not just honesty.

◆ The action is a dial. Delay payouts · rolling reserve · volume caps · proof of fulfilment · offboard. And payout speed is also a growth lever — good merchants get fast money as a benefit, risky ones fund their own exposure.

◆ Don’t quote a payout number. ~2 business days is the common US default, not a policy — it varies by country, by account age, and is itself risk-adjusted. Safe phrasing: “rolling, a couple of days in the US, longer in some markets.”

🧮 Calibration & imbalance
Stripe named “calibrated probabilities” explicitly — this is the differentiator.
Say this“At a 0.3% base rate I probably wouldn’t resample — low probabilities are the correct output. I’d keep natural prevalence, train on log-loss, evaluate with PR-AUC rather than accuracy, and handle the imbalance at the threshold instead of in the training data.”
If probed → AUC measures ranking, calibration measures whether 0.03 means 3% · downsample for compute only, then correct the intercept by ln(r) — exact and free · avoid SMOTE: fraud has many attack modes and categorical features, so interpolation invents structure · check calibration by decile in the tail, where you actually act · Platt vs isotonic · recalibrate weekly, retrain quarterly.
The trapSaying “SMOTE” for imbalance and “expected loss” for thresholds. Those contradict — resampling shifts the base rate and inflates the probabilities the threshold depends on. Fix by not resampling, or by recalibrating.
Imbalance is 3 problemsOptimization (mostly a myth for GBM/logistic) · evaluation (fix with PR-AUC) · decision (fix with the threshold). Resampling only ever touches the first.
What’s actually hard is the absolute number of positives, not the ratio — and resampling doesn’t change that.
The thresholdp* = C_FP / (C_FP + C_FN), where C_FN ≈ amount + dispute fee.
⚠️ State your C_FP assumption. If it’s mostly lost margin it scales with amount; if it’s mostly customer friction it doesn’t — and that determines whether the threshold falls or rises with ticket size. Best answer: measure C_FP from the let-through holdout rather than assuming it.
ProductionLabels lag, so watch the score distribution (PSI) as the leading indicator and confirm with calibration by decile once labels mature. Calibration drift → recalibrate (cheap). Discrimination drift → retrain (expensive).
